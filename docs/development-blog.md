# 从高保真原型到云端可运行：鲜达集市微信小程序开发实录

## 开篇

鲜达集市是一款面向作品展示和求职面试演示的生鲜商城微信小程序。它没有把目标定为一开始就做成完整电商平台，而是围绕一条清晰的用户路径展开：浏览商品、搜索和分类筛选、加入购物车、填写地址、提交演示订单，再从订单中心查看订单状态。

项目最终采用 uni-app、Vue 3、Pinia 和 uniCloud 阿里云实现。前端保留了较强的本地演示能力，商品、地址和订单又可以同步到云端；支付和配送采用明确的演示模式，不接入真实微信支付，也不产生真实配送承诺。这样既能完整展示电商业务闭环，又避免在作品展示阶段引入支付、配送和复杂售后带来的合规与运维成本。

## 一、先确定产品边界

项目最初的需求是一个简易生鲜商城，后来逐步明确为“可操作的微信小程序作品”。需求确认过程中，最重要的决定不是增加功能，而是收缩范围：首期只保证微信小程序移动端，游客可以浏览商品，但进入购物车、结算和下单流程时需要完成演示登录；收货地址手动填写，不调用微信地址授权；点击下单后不进行真实付款，而是直接创建演示订单。

商品被划分为水果、蔬菜、肉禽蛋奶、水产、粮油调味、熟食及其他六类，准备了三十多件示例商品。每件商品除了名称、价格、库存和单位，还包含规格、产地、包装或净重、保鲜提示等信息。库存不超过 10 件时显示库存紧张，缺货、下架、库存不足和价格变化都需要在界面中给出明确反馈。

订单业务也采用适合演示的规则：当前演示中满 29 元免配送费，未满时收取 3 元配送费，配送时段为当天 10:00-12:00 和 16:00-19:00。订单提交后进入“待备货”，后台可以继续演示备货、配送、完成、取消和退款申请等状态变化。

## 二、先做原型，再固化购物闭环

开发前先完成了 PRD、设计说明和技术方案，并制作了高保真 HTML 原型。原型阶段重点验证的是页面关系和交互顺序，而不是立即连接数据库。页面结构确定为：

```text
首页
├── 搜索页
├── 分类商品列表
│   └── 商品详情
│       ├── 加入购物车
│       └── 立即购买 -> 确认订单
├── 购物车
│   └── 确认订单 -> 演示下单成功
└── 我的订单
    └── 订单详情
```

原型阶段重点检查了几个容易出错的交互：详情页“立即购买”只结算当前商品，不改变购物车其他商品的选中状态；购物车金额只计算选中且有效的商品；下单成功后只移除已经提交的商品；提交失败时保留地址、备注和购物车内容。

视觉上采用清新的绿色作为主色，橙色强调价格和库存提示，页面优先按照 390px 手机宽度设计。经过多轮调整，商品、购物车和订单页面统一使用卡通生鲜分类插画，而不是 Emoji 或不稳定的远程商品图片。这样可以避免图片加载失败，也让订单详情中的商品图标保持一致。

## 三、从原型落地到 uni-app

用户端工程位于 `fresh-shop-minipro`，主要技术结构如下：

- `src/pages`：首页、分类、搜索、商品详情、购物车、确认订单、订单和地址等页面；
- `src/components`：商品卡片等复用组件；
- `src/stores`：Pinia 商城状态；
- `src/utils/commerce.ts`：金额、库存、订单等业务计算；
- `src/utils/cloud.ts`：云端调用和本地演示数据的统一入口；
- `src/data/products.ts`：示例商品和分类代表图映射；
- `uniCloud-aliyun/cloudfunctions/shop`：商城云对象；
- `uniCloud-aliyun/database`：商品、用户、地址和订单数据表结构。

商品、购物车和订单信息在前端使用统一的数据结构。购物车条目保留商品快照用于展示，但最终价格和库存不能只相信前端缓存。订单提交时，云端会重新读取商品数据、校验上下架状态和库存，并以云端价格计算订单金额，再执行库存扣减和订单写入。

## 四、从本地演示数据接入 uniCloud

项目早期允许使用 mock 数据，目的是先让界面和购物闭环快速跑通。随着功能稳定，后台能力逐步迁移到 uniCloud：

1. 创建并绑定阿里云服务空间；
2. 上传 `shop` 云对象；
3. 上传 `fresh_products`、`fresh_users`、`fresh_addresses` 和 `fresh_orders` 四个 schema；
4. 通过云对象首次读取商品时自动初始化示例商品；
5. 地址保存、订单创建、订单查询和管理员操作改为写入云数据库；
6. 在云端环境变量中配置管理员密钥和 AI 服务密钥，密钥不进入前端代码。

这个阶段遇到的最大问题是“云数据库明明有配置，但页面一直读不到数据”。排查后发现，使用 `npm run build:mp-weixin` 生成目录并手动导入微信开发者工具，适合查看构建结果，却不适合直接联调 uniCloud，因为这种方式可能没有注入 HBuilderX 的 uniCloud 运行时，前端就会回退到本地演示数据。

因此，当前联调方式是：在 HBuilderX 中绑定服务空间后，通过“运行到小程序模拟器”启动微信开发者工具。修改前端后重新运行或构建，修改云对象后重新上传部署；不需要每次重新导入整个项目。

## 五、前端页面和业务问题的多轮修正

真实运行后，问题主要集中在移动端布局和状态同步，而不是单一的语法错误。项目经历了几轮针对性修正：

- 调整底部导航宽度，避免导航文字显示不完整；
- 修正首页“查看更多”的位置，让它贴近区块右侧；
- 将登录入口放入订单相关页面，避免被首页布局遮挡；
- 缩小过长的右侧操作区域，并让按钮文字垂直居中；
- 修正返回按钮、购物车结算按钮和删除按钮的对齐方式；
- 将价格、配送券、选择时间和“去逛逛”等内容统一为更稳定的右对齐或居中布局；
- 修正收货人、手机号和长地址的截断与换行；
- 修正保存地址点击无反应、订单和地址没有写入云端的问题；
- 处理旧本地缓存覆盖新商品图标的问题；
- 增加微信开发者工具对 `subPackages` 配置的兼容处理。

这类问题说明，浏览器中的 H5 页面和微信小程序模拟器并不是完全相同的运行环境。H5 验证了业务逻辑和基础布局后，还必须在微信开发者工具和真机上检查安全区域、固定底栏、滚动高度、文字换行和触摸区域。

## 六、AI 食材识别助手的接入

AI 助手最初只是一个演示入口，后来接入了阿里云百炼的千问视觉模型。当前流程是：用户选择一张食材图片，前端先进行压缩，再通过 `uniCloud.uploadFile` 上传，随后调用 `shop` 云对象的 `recognizeIngredient` 方法。云对象从云端读取图片，转换为模型需要的格式，调用千问视觉接口，并将识别结果返回给页面。

模型名称默认使用 `qwen-vl-plus`，也可以通过云端环境变量调整。API Key 只配置在 uniCloud 服务空间的 `DASHSCOPE_API_KEY` 环境变量中，前端不会接触密钥。云函数还加入了图片下载、模型请求和整体流程的超时保护，避免第三方服务异常时页面一直处于加载状态。

需要明确的是，AI 识别属于用户主动使用的第三方服务。正式发布前，隐私政策和微信公众平台的隐私保护指引应说明图片会上传到云端并发送给阿里云百炼处理；同时应给出识别失败、服务未配置和请求超时等可理解的提示。

## 七、测试和质量检查

项目当前已经完成以下验证：

- `npm test` 单元测试通过；
- `npm run build` 管理后台构建通过；
- `npm run build:mp-weixin` 微信小程序构建通过；
- `node --check uniCloud-aliyun/cloudfunctions/shop/index.obj.js` 云对象语法检查通过；
- H5 页面能够打开并识别商品卡片；
- 可以从商品卡片进入详情页；
- 地址和订单能够写入云数据库；
- 订单列表和订单详情能够展示分类代表图标。

测试重点不是只检查页面能否打开，还包括重复加购是否合并数量、数量是否不能超过库存、金额是否只计算选中商品、地址缺失时是否阻止提交、订单创建后购物车是否正确扣除，以及订单状态变化后前台是否能刷新。

微信小程序构建时仍可能出现不支持 `strong` 标签选择器等非致命提示。代码检查中还有 JavaScript 压缩和组件按需注入等优化建议，但这些不影响当前作品展示和基本运行。正式上传前仍应完成微信开发者工具中的编译、预览、真机检查和版本上传。

## 八、当前项目状态

现在的项目已经不是只有静态页面的原型，而是一个具备前台购物闭环、基础云端数据能力、简单商家管理能力和 AI 识别入口的演示型小程序：

- 前台可以浏览商品、搜索、分类筛选、加购、填写地址并提交演示订单；
- 地址、订单和商品数据可以通过 uniCloud 保存；
- 云对象会在下单时校验库存和云端价格；
- 管理后台可以进行商品上下架、价格库存调整和订单状态管理；
- AI 助手可以通过千问视觉模型识别用户上传的食材图片；
- 支付、配送、真实微信登录和正式商家运营体系尚未纳入当前作品范围。

当前商家后台入口仍是本地 `admin.html`，如果未来需要让商家在线访问，需要把后台迁移为 uni-app 云端页面，或部署一个带认证的后台服务。这项工作可以在小程序上传后继续进行，不会阻塞当前版本的展示和提交。

## 九、上线前还要做什么

作品展示版上线前，建议按以下顺序收尾：

1. 确认隐私政策中的运营主体、联系方式和 AI 第三方处理说明；
2. 确认 uniCloud 服务空间中已经配置 `DASHSCOPE_API_KEY`，并删除不用的旧模型环境变量；
3. 重新上传最新的 `shop` 云对象和数据库 schema；
4. 使用 HBuilderX 运行到微信开发者工具，检查云端商品、地址和订单数据；
5. 用虚拟姓名、手机号和地址完成一遍完整演示，避免使用真实个人信息；
6. 在模拟器和真机分别检查窄屏布局、底部安全区、图片和 AI 识别；
7. 确认页面文案不会暗示真实支付、真实配送或真实售后；
8. 备案、隐私保护指引和小程序类目资料准备完成后，再提交微信版本审核或上传。

## 结语

这个项目的核心经验，是把“看起来像商城”逐步推进到“能够完成一次完整操作”。先通过原型确定购物闭环，再用 uni-app 组织页面和状态，最后把关键数据交给 uniCloud 校验和保存，能够在控制复杂度的同时获得比较完整的工程展示效果。

对于作品型项目，真实支付、复杂营销和大规模运营并不是必选项。更重要的是明确边界、保证流程可操作、处理异常状态、保护密钥和用户信息，并且能够解释每次技术选择背后的原因。鲜达集市目前正是沿着这条路线完成的。
